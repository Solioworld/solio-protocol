# Subgraph Schema Entities


## Platform (Entity)

- Core Configuration Hub: Stores platform-level settings (factory/admin/treasury addresses, tax rates).
- Supports Token Standards: Links to TokenType entities (e.g., ERC20 implementations).
- Bonding Curve Registry: Manages supported bonding curve algorithms via BondingCurveType.
- Metrics: Tracks total deployed tokens and network metadata (deployment block, chain ID).

```graphql copy
"Platform Info"
type Platform @entity {
  "Platform Id Is Factory Contract Addr e.g. 0xaddr"
  id: Bytes!
  "Blockchain Network e.g. bsc,base"
  network: String!
  "Deploy Hash , e.g. 0xHash"
  deployHash: Bytes!
  "Platform Factory Contract Address e.g. 0xAddr"
  factory: Bytes!
  "Platform Admin Address e.g. 0xAddr"
  admin: Bytes!
  "Platform Treasury Address e.g. 0xAddr"
  treasury: Bytes!
  "Platform Route Contract Address e.g. 0xAddr"
  route: Bytes!
  "Current Mint Tax Rate, base 1e6, e.g. 0.01 = 1%"
  mintTax: BigDecimal!
  "Current Burn Tax Rate, base 1e6, e.g. 0.01 = 1%"
  burnTax: BigDecimal!
  "Init Block Num, e.g. 10006015..."
  startBlockNum: Int8!
  "Block Timestamp, unix second e.g. 1733725032"
  startBlockTime: Timestamp!
  "Token Type List"
  tokenTypes: [TokenType!] @derivedFrom(field: "platform")
  "Bonding Curve Type List"
  bondingCurves: [BondingCurveType!] @derivedFrom(field: "platform")
  "Token Count"
  tokenCount: Int8!
}
```

- Token Standard Definition: Specifies protocol standards (e.g., ERC20) and their implementation contracts.
- Platform Association: Bound to a parent Platform entity.


- Pricing Algorithm Template: Defines mathematical models for token mint/burn pricing (e.g., linear/exponential curves).
- Parameter Encoding: Stores ABI-compatible encoding rules for curve parameters.

```graphql copy

  "Curve Parameter Encoder, e.g. (uint256,uint256)"
  encoder: String!
  "Bonding Curve Type Implement Contract Address e.g. 0xAddr"
  implement: Bytes!
}
```

## Hook(Entity)

- Custom Logic Modules: Attaches external contracts to tokens for added functionality (e.g., whitelists, fee modifiers).
- Immutable Configuration: Stores initialization data and encoding schemas.

```graphql copy
"Token's Hooks, Attention! Hook can deploy by user, notice hook implement, hook may change data after deploy"
type Hook @entity(immutable: true) {
  "Token Address-Hook Address Concat Hash , e.g. 0xBytes32"
  id: Bytes!
  "Token Entity Id"
  token: Token!
  "Hook Contract Address , e.g. 0xAddr"
  address: Bytes!
  "Name, get when this token deploy, e.g. whitelist"
  name: String!
  "encoder, get when this token deploy, e.g. (uint256,string)"
  encoder: String!
  "init Data, get when this token deploy, e.g. 0xData"
  initData: Bytes!
}
```

## Key Relationships

- `Token` ↔ `Platform`: Tokens inherit platform-level config (taxes, curves).
- `Token` ↔ `Swap`/`Transfer`/`Kline`: Transactional entities update token metrics in real time.
- `Account` ↔ `Token`: User balances and activity are scoped per token.
- `Hook` → `Token`: Hooks extend token logic without modifying core contracts.

>This schema provides a structured view of platform operations, token economics, and on-chain activity for analytics and dashboards.

### Explore Schema Fields in Detail

For developers seeking to interact deeply with the data model, each entity’s schema includes comprehensive field annotations. These annotations clarify:
  - Data semantics(e.g., `mintTax: BigDecimal!` explains tax rate storage with a base unit of 1e6).
  - Field relationships(e.g., `token: Token!` links a `Swap` event to its corresponding token).
  - Formatting rules(e.g., `id: Bytes!` for contract addresses vs. `id: Int8!` for incremental IDs).

**Lookout!** When querying address-based fields (e.g., `id`, `user`, `platform`, `token`), **always use lowercase letters**. The subgraph stores addresses in lowercase format, and uppercase characters may result in empty data.

To leverage these details, inspect the schema definitions directly—each field is documented inline with usage context, technical constraints, and illustrative examples. This granularity ensures clarity when querying or extending the subgraph.
